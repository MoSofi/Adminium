A guest signed in by an emailed link can now read their own details. Reading "my details" answered 503 when the details showed the guest's email address or first and last name, which are masked as personal data, although changing the same details answered them in full. The guest's own row is now shown as it is to the session their sign-in link (or a confirmed emailed code) opened, whether it is read as a list, read by id or answered after a change; nobody else gains anything from it: another signed-in guest, a guest found by what they know who has not confirmed the emailed code, an order's own link and a visitor who is not signed in still read none of it. A guest found by the details they typed (a phone, an address) reads those same details back before confirming any code, and nothing else masked, only while their record still holds what they typed: once the desk changes one of those details, that session ends and the guest finds themselves again. A session confirmed by an emailed code likewise ends once the record no longer holds the address the code went to, as a session opened by an emailed link already did. A change's answer never shows more than a read of the same row would.

An app, or an endpoint made in Studio, that shows a column masked as personal data to signed-in guests who have not all proved their mailbox is now refused where it is written, naming the column, instead of answering 503 to the first guest who asks: a guest's own records need the `verified` level, and the sign-in row itself may show such a column only when signing in is by an emailed link, or when it is a detail the guest types to be found.
